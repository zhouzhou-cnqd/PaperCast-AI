- 播客生成：在线场景 **≤ 3–5 分钟**（分阶段进度可见），当前 16 分钟且无进度反馈

## 5. 专项 A：向量检索 + 向量数据库（用户已决策）

### 5.1 选型建议

| 组件 | 首选 | 依据 | 状态 |
|---|---|---|---|
| 嵌入模型 | **BAAI/bge-m3**（本地 GPU） | MIT 许可；100+ 语言**跨语言检索**（中文提问→英文论文，正是我们的场景）；1024 维；8192 token 上下文；稠密+稀疏混合能力 | 【已联网核验】许可/能力；权重 ~2.3GB 下载**待用户授权**；本机实测待做 |
| 嵌入备选 | 云 API（DashScope text-embedding 系列 / 硅基流动 BGE） | 部署到 Sites 后无 GPU 时的替代；按量计费 | 【待核验】具体型号/价格/出口 |
| 向量库（本地 PoC） | **Chroma**（pip 安装，本地持久化，Apache-2.0） | 零部署、几十行代码接入；221 证据块规模绰绰有余 | 【已联网核验】定位；接入实测待做 |
| 向量库（Sites 部署） | 待 S2/S6 核验后定 | Sites 函数能否装 chromadb/持久化未知；**保底方案**：预计算嵌入存 JSON/数据库，函数内 numpy 余弦暴力检索（221×1024 维毫秒级，规模上完全可行） | 【待核验】 |

> 诚实说明：当前单论文 221 块的规模，暴力余弦检索已足够快；引入向量数据库的价值在于
> ① 多论文/知识库扩展 ② 持久化与元数据过滤（按页码/章节过滤）③ 比赛技术栈完整性。方案按此定位设计，不夸大规模需求。

### 5.2 实施设计

1. **索引构建**：`evidence_pool.json`（221 条，含 block_id/page/section/quote）→ bge-m3 批量编码 →
   Chroma collection（metadata：evidence_id/page/section/paper_id）；解析完成后自动建库，产物落 `outputs/vector_index/`
2. **检索链路**：中文提问 → bge-m3 编码 → 向量 top-k（k=8）→ **混合重排**（向量分 + 现有关键词命中加分，保留词表作为稀疏信号而非删除）→ top-5 交 LLM；保留"无证据短路"与"引用代码校验"两道防线不变
3. **上下文融合**：当前播放段落的 evidence_ids 作为检索加权项（而非现在的"空检索才兜底"），更符合"听到哪问到哪"
4. **评测集（验收标准）**：整理 ≥15 个中文问题（含本次实测暴露的"采用的核心方法是什么"、同义改写、跨章节、不可回答类），
   人工标注应命中的证据块；**验收：可回答问题 top-5 召回 ≥90%，不可回答类仍正确拒答**；对照组 = 现有词表检索，结果记入 experiment_log
5. **适配器化**：新增 `retrieval_adapter.py`，接口 `retrieve(transcript, context) -> list[Evidence]`，
   关键词实现与向量实现可切换（Sites 部署时换云嵌入/暴力余弦实现，导师逻辑零改动）

### 5.3 风险

- bge-m3 权重下载 ~2.3GB（免费，需授权）；GPU 显存增量约 2–3GB（与 TTS 共存在 8GB 内，需实测）
- 换嵌入模型 = 全库重建（维度/语义空间绑定），选型一次定准
- Sites 无 Python 重依赖时的降级路径已备（预计算 + 暴力余弦），不阻塞主流程

## 6. 专项 B：TTS 等待久（体验最大短板）

### 6.1 延迟账本（实测拆解，长回答 99.4s 案例）

ASR 3.5s + 检索 <0.1s + LLM 数秒 + **TTS ≈80s** + 传输/加载 ≈1s → TTS 占 80%+，是唯一值得大动的环节。

### 6.2 三层方案（按投入产出排序）

| 层 | 方案 | 预期效果 | 成本 | 状态 |
|---|---|---|---|---|
| B1 **回答长度预算**（先做，半天） | prompt 硬约束"≤3 句/≤120 字"+代码侧超长截断重生成；导师回答本就该口语化短句 | TTS 时长直接砍半以上（120 字≈25s 音频≈45s 合成 → 仍不够，需 B2） | 0 | 待做 |
| B2 **分句流水线**（本地立即可做，1 天） | 回答按句切分 → 第 1 句先合成先播放，后续句**边播边合成**（生产者-消费者队列）；首句通常 ≤20 字 → 合成 ≈5–8s；配合 B3 填充语音掩盖 | **TTFA 从 80s → 5–8s**；本地方案，零 API 费用 | 0 | 待做 |
| B3 **云端流式 TTS**（部署期切换） | DashScope **qwen3-tts-flash**（SSE 流式）或 cosyvoice-v3-flash；第三方实测 TTFA 97–120ms（本地最优环境），服务端到端 250–400ms | **TTFA ≤1s**（含网络）；与 Sites 部署天然契合 | 按量计费【价格待核验】，需用户授权 | 【已联网核验】模型存在/流式能力；音色表与本地预设不同，需试听对照 |

> 注意：97ms 是厂商/第三方在最优环境的 TTFA，不等于我们生产链路端到端延迟；上表已区分口径，验收以**自测端到端 TTFA** 为准。

### 6.3 验收标准

- 本地阶段（B1+B2）：真人提问 → 首个回答音节 **≤8s**（当前 15–99s）
- 云端阶段（B3）：**≤3s**；双音色仍可区分（用户试听）；费用记录入日志
- 播客批量合成不受影响（离线场景保持整段合成质量）

## 7. 专项 C：人性化处理

| 项 | 现状 | 目标设计 | 工作量 |
|---|---|---|---|
| 意图路由 | "你好你好"被冷拒"论文未提供" | 前置轻量分类（规则+LLM 单次调用）：寒暄→友好回应+引导提问示例；论文问题→检索问答；无关问题→礼貌说明范围 | 0.5 天 |
| 即时反馈 | 松开按钮后干等 15–99s | ① 松开即播预合成短语"好的，我查一下论文"（Uncle_Fu 音色，启动时预生成缓存）② UI 阶段进度：转写中→检索中→思考中→合成中（后端分阶段上报或前端按耗时估计） | 0.5 天 |
| 回答可打断 | 只能等播完或点跳过 | 回答播放中可再次按住说话追问（打断当前回答，上下文延续）；"跳过"按钮已有 | 0.5 天 |
| 恢复过渡 | 直接跳回原位置 | 回答播完播 0.5s 过渡提示音或"我们继续"，再恢复播放 | 0.2 天 |
| 失败话术 | 直接抛错误字符串 | ASR 空转写→"没听清，能再说一遍吗"；LLM/TTS 失败→道歉+文字回答兜底显示；网络错误→重试按钮 | 0.3 天 |
| 提问引导 | 无 | 导师面板显示 2–3 个基于当前段落的建议问题（点击即问，降低首次使用门槛） | 0.5 天 |
